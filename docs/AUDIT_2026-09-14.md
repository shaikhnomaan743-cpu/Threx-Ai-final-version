## 2. No training script could run

Every script in `scripts/` imported `cybersentinel_backend.app.*`. The installed
package is `app`. `ModuleNotFoundError` on every one.

`scripts/train_dga.py` additionally had a **syntax error** at line 145 — a bare
`- CryptoWall, TeslaCrypt, ...` line that was meant to be a comment. That file
could never have been executed in its committed state, meaning the shipped
`dga_classifier.joblib` came from some earlier, unversioned edit.

This matters beyond tidiness: the PS requires a reproducible training and
validation approach. As shipped, a reviewer cloning the repo could not retrain
a single model.

**Fixed.** Corrected the syntax error; rewrote imports across all of `scripts/`.
All training scripts now run.

## 3. Throughput and latency were reported by mixing separate test runs

`scripts/measure_throughput.py` ran three configurations, then took
`max(flows_per_sec)` from one and `min(p95_latency)` from another and printed
them together. The README then presented them as one result.

That is also the explanation for `p50 = p95 = 12.93 ms` in the README — a real
latency distribution never has an identical median and 95th percentile. Those
two numbers came from different runs.

**Fixed.** The reporter now prints one sustained run and one burst run, each
with its own p50/p95/p99, and never mixes them.

**Correction to an earlier claim of mine:** I previously told you the 12.93 ms
figure was inflated by `await asyncio.sleep(0.01)`. That was wrong. The two
sleeps in the codebase are in `broadcaster._send_history` (new-subscriber
replay) and `ingest_pcap_file` (replay pacing) — neither is inside the timed
region of `process_flow`. The latency figure was never sleep-inflated. The
problem was the cross-run mixing above.

### Measured, single-run, on this container

| Run | flows/sec | p50 | p95 | p99 |
|---|---|---|---|---|
| Sustained (serial) | 279.0 | 1.69 ms | 17.76 ms | 20.93 ms |
| Burst (no pacing) | 198.0 | 1.69 ms | 18.69 ms | 21.50 ms |

180 flows from `lab_mixed.json`, zero drops.

**Your real numbers are better than the ones you were claiming.** Throughput is
~3x the advertised 88.6 flows/sec and p50 is ~7x faster than the advertised
12.93 ms. Only the tail is worse: p95 ≈ 18 ms, not 12.93 ms. Re-run this on
your own hardware and quote whatever it prints — the deck should say something
like "279 flows/sec sustained, p50 1.7 ms, p95 17.8 ms, p99 20.9 ms, 0 drops,
measured on 180 lab flows," which satisfies PS constraint (d) explicitly.

## 4. The DGA classifier's AUC of 1.0 is a benchmark artifact — NOT FULLY FIXED

Three findings, in order of discovery.

**(a) The model had 2 trees.** `num_boost_round=100` with
`early_stopping_rounds=10` halted at round 2. Also, that kwarg was removed in
LightGBM ≥ 4 — the script would now raise. *Fixed:* switched to the callbacks
API and disabled early stopping outright; added 5-fold stratified CV so the
reported figure has an error bar.

**(b) Cross-validation confirmed it is not a split artifact.** 5-fold CV AUC
came back 0.9998 ± 0.0005. So the task itself is trivial.

**(c) Root cause: domain-label length separates the classes perfectly.**

```
benign  (alexa_top_1m.txt): n=1000, mean label length  6.6, max 13
dga     (generated):        n=1000, mean label length 21.5, min 12
benign with label >= 12 chars: 20 / 1000
dga    with label <  12 chars:  0 / 1000
```

A single threshold at 12 characters classifies this dataset almost perfectly.
The model never needed entropy or n-grams; it learned "long means malicious."

Two data problems underneath:

- `data/models/alexa_top_1m.txt` is 1000 hand-picked short popular domains
  (`google.com`, `youtube.com`, …), not a real Tranco sample. Real Tranco has
  plenty of long labels.
- The "DGArchive samples" are **generated inside `train_dga.py`** by a random
  consonant-heavy string function — they are not DGArchive data, despite what
  the README and the literature review say. Every generated domain is 12–30
  characters by construction.

I added a dictionary-DGA generator (suppobox/matsnu/gozi style — concatenated
English words, so entropy sits inside the benign range) because the shipped
model would miss that entire live family. AUC stayed at 1.0, because my
dictionary domains are also ≥12 characters. **The length confound dominates
everything and cannot be fixed without real data.**

### What you must do

1. Download a real Tranco top-1M sample (`https://tranco-list.eu`) and take
   10–20k domains, keeping the natural length distribution.
2. Get real DGArchive samples, or at minimum generate across the full realistic
   length range (6–30 chars) including dictionary families.
3. Retrain and **report the honest CV AUC**, whatever it is. Something near
   0.93–0.97 with a real corpus is a far stronger claim than 1.0 on a corpus a
   length threshold solves.

Until then, do not put the DGA AUC on the deck as a headline number. Say the
detector is implemented and that validation against a real corpus is in
progress. That is defensible; 1.0 is not.

## 5. Not started — the unidirectional ablation

The direction-stripping experiment we discussed is not in this drop. It is the
strongest research claim available to you, and it is unaffected by the DGA data
problem above, so it remains worth doing.

Note while building it: `syn_to_ack_ratio` (ddos_detector), `amplification_ratio`
(ddos_detector) and `byte_ratio_outbound` (exfil_detector) are all two-sided
features. On a genuine one-way tap the return packets may never arrive, so these
degrade silently. That is both the bug and the experiment.
